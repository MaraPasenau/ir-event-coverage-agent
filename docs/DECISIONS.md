# Decisions and why

| # | Decision | Reason | Alternative rejected |
|---|---|---|---|
| 1 | Build the agent in Dataleap, not as a separate codebase | The task is to demo an agent on Dataleap; Dataleap provides harness, agent DB, triggers, approvals | Standalone Express/Postgres app (Victor's agent-studio pattern) — reference only |
| 2 | Rules live in four Dataleap skills, control flow in the agent prompt | Skills load only in the step that names them (token cost); rules change without touching the agent; mirrors Victor's skill-selector pattern in Dataleap's native format | One monolithic prompt |
| 3 | Private Attio workspace `b2v`, synthetic people, Testperson 1–3 as DRIs | Employer CRM and real investors must not enter a third-party demo | Connecting the company Attio |
| 4 | One shared coverage list for all events, linked via `coverage_event` | Attio allows the same record several times in one list; one list per event would duplicate ~90 fields per event | One list per event (Codex' original fixture) — kept as fallback |
| 5 | Tiers express potential and coverage priority, not eligibility; 50k DI ticket is a booster, unknown never disqualifies | Prospecting agent, not a qualification gate; founders without known investments are valid targets | Hard thresholds as core criteria |
| 6 | Identity resolution before any create; name-only matches create a flagged record with Conflict, never merge | Avoid duplicates and wrong merges; humans resolve conflicts in Attio | Merge on name |
| 7 | Every debrief creates an Attio note on the Person, independent of outcome or approval | Conversation history is relationship data; opportunities are a separate business object | Notes only on promotion |
| 8 | Approval by Slack reaction (:+1: / :-1:) from an eligible DRI's `slack_user_id`, bound to the proposal message ts | Dataleap documents reaction-added triggers as the approval pattern; any other reactor is logged and ignored | "approve" typed by anyone in the thread |
| 9 | Clay out of v1; LinkedIn enrichment and web search instead | Clay MCP needs a paid plan; Phase 0 showed Dataleap's LinkedIn tool enriches supplied URLs; synthetic people cannot be enriched by Clay anyway | Custom MCP server wrapping Clay |
| 10 | Luma via organiser CSV export, no live API | Luma API requires Luma Plus and a calendar-scoped key; CSV is the honest first release | Scraping the guest list |
| 11 | No photos in v1 | LinkedIn API does not expose third-party photos; `profile_photo_*` fields stay human-only | Downloading profile images |
| 12 | Voice only after the Slack-file → transcription chain is tested (T11) | Phase 0: both tools present but inactive and untested | Promising voice in the Loom |
| 13 | Write protocol: intent → execute → read-back → verified/mismatch; lookup by idempotency key after ambiguous responses | Caught a real mismatch in 6.1 (Attio truncates timestamps to ms) without replaying writes | Trusting the model's "done" |
| 14 | Cost mode for the remaining build: read-back once per entry, one summary row per step, lowest tool-capable model tier for research | 6.1 cost ~$7 on a $7.50/week plan | Full audit mode throughout |
| 15 | `responsible_dri` not written on investor entities in v1 | Select has no Testperson options and the API cannot add options; the DRI lives on the opportunity | Mapping test DRIs to real team codes |
| 16 | `#event-coverage` is a dedicated channel: only agent briefings and DRI replies. The new-message trigger fires on every message there by design; there is no irrelevant traffic to filter | Dataleap charges per run; a dedicated channel keeps trigger runs equal to real debriefs | Channel-wide trigger on a general channel with keyword filtering |
| 17 | Text and voice debriefs are equal inputs. Voice: transcribe → post transcript → ✅ by the DRI → extract. Text: extract directly. Transcript confirmation and proposal approval are separate gates | An unconfirmed transcript must never create CRM changes | Auto-extracting from the raw transcript |
| 18 | Tier function redefined (demo-v2): A = both core supported, recent, external; B = both core but stale/CSV-only, or one core + recent booster; C = one core, no booster; no evidence = Needs Review (unrated); dated contradiction of a core = Irrelevant | With two core signals per product, demo-v1's B and C were the same predicate and a contradicted core had no tier. `evals/run_evals.py` proves the new function is total over the signal space | Keeping demo-v1 and letting the model break ties |
| 19 | One `rank_products()` (tier → supported count → Gen Cap > DI > Fund) for routing, `proposed_overall_tier`, `selected_product` and multi-product promotion; the debrief ranks only interested products | Three different "strongest product" definitions produced a wrong `selected_product` in T7 | Separate definitions per step |
| 20 | Eligibility requires `slack_user_id`; Testperson 1 is ineligible until mapped; DI attendees fall back to R3/R4 | A routed attendee whose DRI cannot be mentioned or approve is a dead end | Routing to Mara and approving from this chat |
| 21 | R2 iterates `relevant_products` in rank order; R3 ties break by overlaps → load → `dri_code`; Escalated only when no eligible DRI attends with capacity; thin-evidence attendees routed by R4 as "unrated" and listed in a final briefing block | R3-tie escalation contradicted the "everyone gets a DRI" rule; R2 ignored the second product; Needs Review conflated identity conflict with thin evidence | Needs Review never routed |
| 22 | Stage machine made total: 6.4 guarded by empty `proposed_overall_tier`; 6.7 ends at Conversation Logged; 6.8a → Routing Ready (A/B) or Closed (C); 👎 keeps Routing Ready with `proposals.status = rejected` | 6.4/6.5 shared a precondition (re-tiering on rerun); 6.7 skipped a stage, leaving an orphan state after a crash | Adding new stage options in Attio |
| 23 | `slack_messages` registry (ts → kind) written before any dependent write; reaction trigger dispatches by lookup; ✅ or 👍 confirm a transcript, 👍/👎 decide a proposal; approver = the entry's `assigned_dri` | Without message identity the agent decides by emoji, and transcripts were never stored | Emoji-based dispatch |
| 24 | Durable state moves to Attio where possible: human override = `dri_assignment_state = Confirmed` (no agent DB diff); optional attributes `slack_channel_id`, `attending_events` on `ir_dri_people` with fallback to `dri_config`; idempotency keys use `luma_event_id`/normalized name + date, `person_record_id` for angels, domain for organisations; LinkedIn and names compared after normalization; name-only creates are `Pending`, not Verified | The agent DB was lost twice in one day; `sha1(lower(name))` duplicated entities on spelling variants; `luma_url or name` changed the event key when the URL was added later | Keeping all execution state in the agent DB |
| 25 | DRI channels are public `#targets-<firstname>` channels; the private `#coverage-*` channels are retired | Dataleap's shared Slack connection cannot read, post or trigger in private channels (Phase 0, 3rd account); channel membership metadata is not access. In the three-person test workspace, public channels are an acceptable demo constraint | Custom Slack app for the agent (the production answer; documented in STATUS as the upgrade path) |
| 26 | Briefings show "Interests" (the `professional_interests` field: evidenced sectors, investment type, stage/geography, one recent activity) instead of "Worth asking" questions; `data_gaps` and talking points stay internal | An event briefing tells the DRI who the person is and what they invest in; it does not script questions, and ticket sizes are never asked at an event. The interests line is the product of the enrichment step and must be checkable in Attio | Questions derived from data gaps (Codex design) |
| 27 | Profile photos come from the LinkedIn enrichment payload (Crustdata `profile_picture_permalink`), shown only in the Slack briefing, never stored in Attio; best effort with explicit skip logging | Verified 2026-10-17 with Mara's own profile: the field exists and Slack renders it. No scraping, no image search, no extra provider; a failed photo never blocks a digest | Google image search (inaccurate), browser scraping (ToS), Proxycurl (shut down after LinkedIn's 2025 lawsuit) |
| 28 | Step 6.9: after approval the agent drafts the follow-up (Gmail draft, or text in the DRI channel with mailto / LinkedIn / WhatsApp hint by available contact data) and opens a task; the DRI sends and closes with ✅ | Zero human minutes between conversation and a ready draft, while the relationship and the send stay with the human; LinkedIn has no messaging API, so drafts for it are copy text | Automatic sending; phone-first priority |
| 29 | Web-research identity guard: a claim is accepted only if the page names the company and the person or role; same-name hits at other organisations are discarded and logged; rows without a company get no person-level search; LinkedIn matches need confidence_score ≥ 0.8 | Prevents enriching the wrong Anna Müller; makes the discard visible in run_log | Trusting the search ranking |
| 30 | Voice transcripts pass a deterministic glossary normalizer (products, fixed terms, attendee full names; phonetic + edit distance; never function words, negations, short tokens or partial names) before the confirmation request; changes are shown as "Changed: a → b" and the DRI corrects single words instead of retyping | First live voice test: Whisper-class ASR rendered "Gen Cap" as "Jinka" and "Fund-Themen" as "Fun-Themen". Vocabulary biasing at the ASR (Whisper prompt / Deepgram keyterm) is the first line; the normalizer is the second; targeted questions the third | Confirming or retyping whole transcripts |
| 31 | Fifth skill IR Operator: how the agent reads the operator's chat messages (intent first, short affirmatives approve what is pending, most plausible reading stated in one line, no re-audit, eight-line answers) | The agent spent whole runs (≈$1.50 each) deliberating over "Yes" and dictated messages; the Slack side already reads intent, the chat side did not | Longer prompt, stricter command grammar for the operator |
| 32 | Follow-up drafts are revised by intent from text or voice replies (versions, Gmail draft updated in place); sending is a workspace setting `followup_send_mode`, default `draft` (agent never sends); `send_on_explicit` sends only on an explicit send instruction from the DRI's own mailbox to the CRM address | The DRI should be able to say "change this word" instead of retyping; sending stays a human act by default because the relationship belongs to the DRI, with an opt-in for teams that want it | Auto-send after approval |
